# ADR-0009: Board Portal Duplicate — Backend-Generated Descendant IDs

- **Status:** Accepted
- **Date:** 2026-09-18
- **Source:** `tasks/todo.md` №16

## Context

`docs/decisions/0001-v1-scope.md` and `tasks/current-state.md` settle that "the
frontend generates ids (UUIDv7); IDs stay an input to every `create_*`" — every
other write command in this codebase (`create_note`, `create_child_board`,
`move_selection_to_board`, …) takes caller-supplied ids for everything it
creates.

Duplicating a Board Portal's whole subtree breaks that pattern: the set of rows
to create is not known to the caller. A board can contain an arbitrary,
recursively-nested tree of notes, images, embeds, file cards, filesystem
aliases, and further Board Portals (each with its own nested board). The
frontend holds only the *root* portal it right-clicked or copy/pasted — it has
no visibility into what's inside the board it is duplicating, let alone what's
inside a board nested three levels down.

## Decision

`DuplicateBoardInput` carries exactly two frontend-generated ids: the new
board's id and the new root portal card's id — the two objects the caller
needs to place on the canvas and reference for undo. Every other id created
during the recursive copy (each duplicated card, each nested duplicated board)
is generated by the backend with `uuid::Uuid::now_v7()`, inside the same
transaction that discovers the row needs copying.

This is a deliberate, narrow exception to "the frontend always generates ids,"
justified because:

1. **The transaction is the only place that knows the shape.** Reading the
   source board's live card set, and recursing into any nested Board Portal's
   own target board, both require a `SELECT` against the database. There is no
   way for the frontend to pre-compute "I will need N ids" without first doing
   that same read itself — which would either duplicate the whole read-then-copy
   logic on the client, or force a synchronous round trip before the copy could
   even start (an id-reservation RPC), for no benefit: nothing outside this one
   transaction ever needs to reference those descendant ids before they exist.
2. **Undo needs no descendant ids at all.** Unlike ADR-0007's mixed-selection
   move, which needs a full receipt to reverse itself, duplicate's undo is the
   existing Trash cascade: `trash_board(new_board_id)` already walks the whole
   subtree by `parent_board_id`/`board_id`, regardless of what ids live inside
   it. The frontend's optimistic UI only ever needs the two ids it already
   generated (to draw the new portal and to trash it on Cmd+Z) — it has no use
   for a card-by-card id list, so there is nothing to lose by not receiving one.
3. **Atomicity already provides the only safety property ids-as-input would
   have bought.** The reason every other command takes frontend ids is
   idempotent replay under IPC retry (a lost response must not create a second
   copy). `duplicate_board` is a single Immediate transaction: a retry after a
   confirmed commit is a caller bug, not a case this contract needs to make
   safe, since nothing partial can ever be observed to retry against.

## Consequences

- `duplicate_board` cannot be blindly replayed with the same "logical" request
  and land the same descendant ids twice — retrying a failed call is safe
  (nothing committed), but retrying a *succeeded* call creates a second full
  copy. This matches `create_child_board`'s and every leaf `create_*`
  command's own retry story (id reuse is the caller's replay guard elsewhere;
  here there is no id to reuse for anything but the root, so the root's reuse
  check — `new_board_id`/`new_portal_card_id` already exists ⇒
  `ConstraintViolation` — is what a naive retry hits, not silent duplication of
  the *first* attempt's descendants, but a full second copy under new ids).
  Acceptable for V1: the paste/duplicate gesture is user-initiated and
  interactive, not a background job that retries unattended.
- Asset ids are never regenerated — copied image/file/embed/cover references
  point at the *same* `assets` row as the original (copy-in model, matching
  card-paste's existing convention, `tasks/lessons.md` 2026-09-18 "Card
  copy/paste"). `asset_service::collect_orphaned_assets` already counts owners
  by `NOT EXISTS` across every asset-owning table, not a per-card cap, so this
  needed no GC change.
- Only the copy's *root* board is renamed "`<title> copy`" (Finder-style,
  unique among the target board's siblings); every nested duplicated board
  keeps its original title unchanged, matching the mental model that a
  duplicate is "the same structure, once, with one new front door."
- Depth is capped at `MAX_DUPLICATE_DEPTH = 32` (`ConstraintViolation` beyond
  it) purely to bound one transaction's work — not a cycle guard: a copy can
  never become its own ancestor, since it is always a brand-new subtree with
  fresh ids, even when pasted onto one of the source's own descendants.

## Alternatives considered

- **Two-phase: reserve ids, then create.** Rejected — adds a round trip and a
  reservation table for a benefit (frontend-visible descendant ids) nothing
  downstream consumes.
- **Frontend recursively fetches the whole subtree first, generates ids client-
  side, then sends a flat list.** Rejected — duplicates the transaction's own
  read work on the client with no transactional guarantee between the read and
  the write (the source could change mid-copy), and does not fit the same
  "atomic, single call" shape as every other multi-row command in this
  codebase (ADR-0007).
